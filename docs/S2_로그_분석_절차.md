# S2 로그 분석 절차

기준 API: `http://localhost:9090`

이 문서는 S2 로그를 수집하고, S1 파일을 제외한 뒤, 배포 전후 차이를 같은 시간대 기준으로 비교하는 운영 절차를 정리한다.
명령 예시는 현재 운영 환경에 맞춰 PowerShell 기준으로 적었고, 본문에서 말하는 `grep`은 같은 의미의 패턴 검색 개념으로 보면 된다.

## 목적

- S2 로그만 골라서 분석한다.
- 재시작 시점과 버전을 확인한다.
- 4 Thread(4T) 적용 여부를 확인한다.
- 배포 전후를 같은 시간대 기준으로 비교한다.
- 초기화 직후 왜곡 구간을 별도 취급한다.

## 전체 플로우

1. 인증: `POST /login`으로 쿠키를 저장한다.
2. 수집: `POST /api/logs/{agent_id}/history`로 대상 날짜 로그를 요청한다.
3. 대기: 약 20초 후 `storage/logs/{agent_id}/{YYYYMMDD}/`에 파일이 생성됐는지 확인한다.
4. 구별: `[RTP_START]` 또는 `[DURATION_GAP]` 건수로 S2 파일 여부를 판별한다.
5. 시점: `AirRecorder v` 또는 `InitInstance` 로그로 재시작 시점과 버전을 확인한다.
6. 4T 확인: `RtpProcessThread worker=`가 `0,1,2,3`으로 모두 찍혔는지 본다.
7. 분석: `DEPLOY_TS` 기준으로 before/after를 나누고 시간대별로 집계한다.
8. 해석: 반드시 피크 시간대의 동일 구간끼리 비교한다.

## 사전 확인

- 대상 에이전트 ID 예시: `PC-1577`
- 대상 날짜 형식: `YYYYMMDD`
- 저장 경로: `storage/logs/{agent_id}/{YYYYMMDD}/`
- 운영 기준은 로그인 후 쿠키를 유지하는 방식이다.
- 현재 서버 구현상 `/api/logs/*`는 인증 미들웨어 예외 경로지만, 운영 절차는 로그인 세션을 먼저 여는 흐름으로 맞춘다.

## 1. 인증

로그인 폼은 `username`, `password` form-data를 받는다. 쿠키는 `access_token`으로 저장된다.

```powershell
$base = "http://localhost:9090"
$cookieFile = "$env:TEMP\\ai-logops-cookies.txt"

curl.exe -c $cookieFile `
  -X POST "$base/login" `
  -F "username=<ID>" `
  -F "password=<PASSWORD>"
```

## 2. 로그 수집 요청

`folder_index=-1`은 전체 폴더 기준 요청이다.

```powershell
$agentId = "PC-1577"
$date = "20260422"

curl.exe -b $cookieFile `
  -X POST "$base/api/logs/$agentId/history" `
  -H "Content-Type: application/json" `
  -d "{\"date\":\"$date\",\"folder_index\":-1}"
```

정상 응답 예시는 다음 형태다.

```json
{"status":"ok","agent_id":"PC-1577","date":"20260422","folder_index":-1}
```

## 3. 수집 대기 및 파일 확인

에이전트가 과거 로그를 묶어서 전송하는 시간이 필요하므로 기본적으로 20초 정도 대기한다.

```powershell
Start-Sleep -Seconds 20
Get-ChildItem "storage/logs/$agentId/$date"
```

파일이 없으면 다음을 먼저 확인한다.

- 에이전트가 접속 중인지
- 대상 날짜가 맞는지
- 로그 보관 경로가 비어 있지 않은지
- 재요청 전에 기존 파일을 지워야 하는 상황인지

## 4. S1/S2 파일 구별

같은 폴더에 `_1.txt` 같은 S1 파일과 `_3.txt` 같은 S2 파일이 섞여 들어올 수 있다. 파일명으로 단정하지 말고, 내용 기준으로 골라야 한다.

판별 기준:

- `[RTP_START]` 1건 이상이면 S2로 본다.
- `[DURATION_GAP]` 1건 이상이어도 S2로 본다.
- 두 패턴이 모두 0건이면 S1 가능성이 높으므로 집계에서 제외한다.

```powershell
$files = Get-ChildItem "storage/logs/$agentId/$date" -File

$s2Files = foreach ($file in $files) {
  $matches = Select-String -Path $file.FullName -Pattern '\[RTP_START\]|\[DURATION_GAP\]' -AllMatches
  if ($matches.Count -gt 0) {
    $file.FullName
  }
}

$s2Files
```

## 5. 재시작 시점과 버전 확인

배포 당일 분석에서 가장 중요한 기준점은 재시작 시점이다. 이전 날짜 로그는 같은 버전인 경우가 많아서 변화 비교에 의미가 없다.

확인 패턴:

- `AirRecorder v`
- `InitInstance`

```powershell
Select-String -Path $s2Files `
  -Pattern 'AirRecorder v|InitInstance'
```

여기서 확인할 것:

- 실제 재시작 타임스탬프
- 배포 후 올라온 버전 문자열
- 재시작이 여러 번 있었다면 분석 구간 분리 필요 여부

## 6. 4T 적용 여부 확인

4T 적용 여부는 `RtpProcessThread worker=` 로그가 `worker=0`, `worker=1`, `worker=2`, `worker=3`으로 모두 존재하는지로 확인한다.

```powershell
Select-String -Path $s2Files -Pattern 'RtpProcessThread worker='
```

판정 기준:

- `worker=0~3` 4줄이 모두 있으면 4T 적용
- 일부만 있으면 비정상 시작 또는 로그 누락 가능성 검토
- 재시작 직후 로그만 보고 결론 내리지 말고 해당 세션 전체를 본다

## 7. 배포 전후 분석

분석 기준은 `DEPLOY_TS`다. 반드시 같은 피크 시간대끼리 비교한다.

예시 원칙:

- `before`: `DEPLOY_TS` 이전
- `after`: `DEPLOY_TS` 이후
- `after` 중 재시작 후 10분은 별도 구간으로 분리

이유:

- 재시작 직후에는 세션 초기화 영향으로 `CODEC_FAIL`이 일시적으로 튈 수 있다.
- 이 구간을 일반 구간과 합치면 배포 효과 해석이 왜곡된다.

권장 비교 방식:

- 동일 시간대 before/after 비교
- 동일 트래픽 밀도 구간 비교
- 피크 시간대 우선 비교

비권장 비교 방식:

- 이전 날짜 전체 평균과 단순 비교
- 재시작 직후 10분을 일반 운영 구간에 포함
- S1/S2 혼합 파일 합산

## 8. 지표 해석 기준

### 서버 패킷 유실

- 네트워크 품질 반영 지표다.
- 쓰레드 수와 직접 연결하지 않는다.

### 클라 패킷 유실

- 큐 지연 또는 드롭 반영 지표다.
- 4T 효과가 직접 나타나는 핵심 지표다.

### `CODEC_FAIL`

- RTP 매칭 지연의 결과 지표다.
- 실질적인 미녹취 판단에 가장 직접적이다.

### Mutex 경합

- 단일 쓰레드 한계를 직접 보여주는 지표다.
- `RtpProcessThread mutex locked` 패턴으로 확인한다.

## 자주 실패한 접근과 교정 기준

| 잘못된 접근 | 원인 | 올바른 방법 |
|---|---|---|
| JWT 수동 생성 (`jwt-result.txt` 키 사용) | 서버가 hardcoded secret 기준으로 검증할 수 있음 | `POST /login` form-data로 로그인하고 쿠키 사용 |
| `grep timeout`으로 이상 탐지 | `RTCP_GRACE BYE`가 통화마다 `"10s timeout"`을 남김 | `RtpProcessThread mutex locked`를 본다 |
| `queue_skip`, `unrecorded` grep | v2 이후 해당 키워드가 사실상 의미 없음 | `CODEC_FAIL`, `[RTP-STATS]` 기준으로 본다 |
| 이전 날짜 로그 분석 | 같은 버전이면 비교 가치가 낮음 | 배포 당일 재시작 전후를 비교한다 |
| `_1.txt`(S1)와 `_3.txt`(S2) 혼용 집계 | 같은 폴더에 함께 수신될 수 있음 | `[RTP_START]`, `[DURATION_GAP]` 건수로 S2만 고른다 |
| Python heredoc와 파이프를 같이 사용 | EOF가 파이프 안으로 파싱될 수 있음 | `python -c "..."` 또는 별도 `.py` 파일 사용 |
| 재시작 직후 10분 통계 포함 | 세션 초기화로 `CODEC_FAIL`이 일시 급증 가능 | 재시작 후 10분은 별도 구간 처리 |

## 실무 체크리스트

- 로그인 쿠키를 먼저 확보했는가
- 대상 날짜 로그가 실제로 내려왔는가
- S2 파일만 분리했는가
- 재시작 시점과 버전을 확인했는가
- `worker=0~3` 4줄을 확인했는가
- `DEPLOY_TS` 전후를 같은 시간대로 나눴는가
- 재시작 후 10분을 별도 처리했는가
- 피크 시간대 기준으로 비교했는가

## 참고 패턴

```text
[RTP_START]
[DURATION_GAP]
AirRecorder v
InitInstance
RtpProcessThread worker=
RtpProcessThread mutex locked
CODEC_FAIL
[RTP-STATS]
```
